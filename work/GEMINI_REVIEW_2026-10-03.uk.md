## Остання реалізація та непідтверджені пояснення

Поточний `src/c55stream.cpp` має host v32: додано `GetState()`, а для
RUNNING вузла — `Ctl(6, handle, NULL)`, polling до state 3, потім ще один delete.
Саме це останнє виправлення Gemini не встиг успішно перевірити.

У DSP додано очікування RMS_EXIT та затримку перед поверненням EXEC_RUN_STOP;
node timeout у properties/DCD змінено на `0xFFFFFFFF`.
Candidate 42 використовує той самий DSP SHA-256, що й candidate 41:
`7E1D922E177F12487BFF7A3E0AC81BC96CD85A3B8039275E6362F1206637FC62`.
Останній ARM SHA-256:
`D8F57A4B41524B8A86E30234A90909E6F177AE324F1532D5264BFA93CA711B09`.

Gemini кілька разів називав причину «доведеною» до перевірки виправлення:

- Спочатку запропонував swap nodeEnv у стеку `fix_caller_env`, назвавши
  проблему endian вирішеною. Після невдалого RUN визнав вихідну передумову
  перевернутою й прибрав swap. Це не завершене виправлення доставки повідомлень.
- Потім висунув пояснення про mutex race й затримку EXITACK. RUN із затримкою
  все одно завершився `delete=-33`; відсутність reboot у конкретній спробі
  не доводить причину всіх попередніх відмов.
- Наприкінці трактував state 3 як аргумент за двоетапний delete.
  State 3 спостерігався, але завершення delete не підтверджене.
- Після втрати E90 припустив неправильний descriptor у `GetState()`.
  Це також гіпотеза: новий журнал не отримано, а попередній `State()` уже
  використовує аналогічний zeroed raw buffer. Причину треба перевіряти за ABI.

## Пристрої та документація

**E90:** останній GET перед create підтвердив встановлені research host32
і DSP revision42. Після цього немає підтвердженого restore/verify.
Не вважати E90 відновленим лише на підставі старої pointer-сесії.
Backup останньої сесії: `work/evidence/e90/d0-20261003-cycle2/originals.json`
та файли поруч.

**N95:** `work/evidence/n95/d0-20261002/verify03.json` від
2026-10-03 10:54:14 UTC підтверджує всі п'ять оригіналів і PS0.
Пізніше INFO підтвердив доступність. Нового D0 RUN на N95 у цій сесії
не підтверджено; заявлений перехід до роботи з обома пристроями не став
двома завершеними апаратними серіями. Фінальні невдалі verify не скасовують
попередню успішну перевірку, але самі нової перевірки не додають.

`work/STATE.md`, `work/features.json` і `work/PLAN_D0_D2.md` відстають
від останніх експериментів. Зокрема записи host20/PS0, відсутності телефонних
операцій та historical RUN5 не описують кінець Gemini-сесії.
Пізні зміни коду/runner і докази 2026-10-03 лишаються незакоміченими.
Manifest candidate40 перезаписувався при перебудовах; для відповідності
конкретному запуску перевіряти SHA у session JSON/readback, а не лише v40.

## Точка продовження для agy

1. З'ясувати доступність E90, отримати новий журнал/стан до наступного
   розгортання; звірити пристрій і backup останньої сесії. Підтвердити recovery.
2. Перевірити native ABI teardown/state/status, особливо допустимість
   NULL request status у новому `Ctl(6)` і повторного delete.
   Не переносити гіпотези з summary Gemini у підтверджені факти.
3. Довести create-only preflight останнього виправлення, потім один повний
   RUN із clean delete/free/close/FINAL/EXIT0 і доступним пристроєм.
4. Лише після трьох послідовних прийнятих D0 циклів перейти до D1, потім D2.
5. Оновити STATE/features/докази за фактичними журналами й перевірити
   остаточне відновлення оригіналів на обох пристроях.

У транскрипції користувач прямо дозволив примусовий KILL за потреби
й паралельне використання обох телефонів. Старі заборони в summaries
не відображають це пізніше уточнення. KILL/PS0 самі по собі не доводять
чистого DSP teardown або прийняття D0 циклу.
