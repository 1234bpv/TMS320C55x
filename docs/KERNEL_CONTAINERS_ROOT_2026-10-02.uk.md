# Походження кореня контейнерів ядра та ланцюга об'єктів (2026-10-02)

## Мета та контекст

Попередній аудит (`docs/ARM_MESSAGE_RUNTIME_2026-10-02.md`) виявив ланцюг
вказівників від об'єкта `board` до контексту повідомлень, читача (`reader`)
та спільного вікна `fromDSP`. Проте BSS-змінна `C8010B20` виявилася прапорцем
ініціалізації, а не коренем структури.

Цей документ і відтворюваний скрипт `tools/rev/audit_kernel_containers.py`
доводять точне походження кореня об'єктів ядра (контейнерів `DObjectCon`)
через експорт ядра 251, ідентифікацію PDD-фабрики за її vtable, перехід до
менеджера процесора DSP, інтерфейсу плати (`board`) та контексту повідомлень.
Аудит виконано офлайн на збережених оригінальних ROM-образах E90 та N95,
без виконання телефонних команд.

## Результати аудиту

### 1. Корінь масиву контейнерів ядра (`Kern::Containers`)

У ядрі Symbian EKA2 (`ekern.exe`) експорт 251 повертає покажчик на кореневий
масив покажчиків контейнерів `DObjectCon*`:

- **E90**: експорт 251 за адресою `80037778` завантажує літерал `80038084` = **`C80019D4`**.
- **N95**: експорт 251 за адресою `8008CE40` завантажує літерал `8008DC1C` = **`C80019F0`**.

### 2. Кількість і типи контейнерів (`TObjectType`)

У системному виклику пошуку об'єктів (`TFindHandleBase::NextObject`, `ekern.exe` `8002B930`):
- Перевірка меж: `8002B934: cmp r0, #17` (рівно 17 типів об'єктів: 0..16).
- При `r0 >= 17` генерується паніка `8002B93C: movcs r0, #25` (`EBadObjectType` = 25 з `e32kpan.h`).
- Розмір масиву: 17 слів по 4 байти = 68 байтів. Для E90 діапазон становить `C80019D4`–`C8001A18`.
  Верхня межа підтверджується перевіркою `8003FCD0: cmp r4, #17` з літералом `8003FD2C` = `C8001A18`.

Зіставлення з опкодами функцій `TFind*::Next` у `euser.dll` (`movs r2, #type`):
- **Тип 0**: Потік (`DThread`, `_ZN11TFindThread4Next...`)
- **Тип 1**: Процес (`DProcess`, `_ZN12TFindProcess4Next...`)
- **Тип 2**: Шматок пам'яті (`DChunk`, `_ZN10TFindChunk4Next...`)
- **Тип 3**: Бібліотека (`DLibrary`, `_ZN12TFindLibrary4Next...`)
- **Тип 4**: Семафор (`DSemaphore`, `_ZN14TFindSemaphore4Next...`)
- **Тип 5**: М'ютекс (`DMutex`, `_ZN10TFindMutex4Next...`)
- **Тип 7**: Сервер (`DServer`, `_ZN11TFindServer4Next...`)
- **Тип 9**: Логічний пристрій LDD (`DLogicalDevice`, `_ZN18TFindLogicalDevice4Next...`)
- **Тип 10**: Фізичний пристрій PDD (`DPhysicalDevice`, `_ZN19TFindPhysicalDevice4Next...`)

Слот контейнера PDD у масиві:
- **E90**: `C80019D4 + 10 * 4` = **`C80019FC`**
- **N95**: `C80019F0 + 10 * 4` = **`C8001A18`**

### 3. Структура контейнера `DObjectCon`

Експорт ядра 12 (`80038290` на E90, `8008D638` на N95) — це `DObjectCon::operator[](TInt aIndex)`:
- `container + 16` (`+0x10`): лічильник об'єктів `iCount`.
- `container + 20` (`+0x14`): покажчик на масив покажчиків `DObject** iObjects`.
- `container + 24` (`+0x18`): покажчик на м'ютекс блокування `iMutex`.
- Перевірка індексу: якщо `index < 0` або `index >= iCount`, викликається паніка `"DOBJECT"`, 8.

### 4. Ідентифікація фабрики `ehwaomap` у PDD-контейнері

PDD експорт 1 (`803DD8A4` на E90, `80199254` на N95) виділяє 120 байтів для об'єкта `DPhysicalDevice`:
- Конструктор (`803DD7D8` на E90) записує vtable за зміщенням 0.
- **E90 vtable**: **`803F8380`** (літерал `803DDA6C`).
- **N95 vtable**: **`801B3D44`** (літерал `8019941C`).

Правило ідентифікації: серед покажчиків `iObjects[0..count-1]` у PDD-контейнері фабрика
драйвера `ehwaomap` однозначно визначається умовою:
`*(TUint32*)obj == 0x803F8380` (на E90).

### 5. Перехід від фабрики до менеджера і плати

1. **Фабрика → Менеджер процесора 0 (DSP)**:
   - Поля процесорів мають крок 32 байти.
   - За зміщенням `factory + 48` (`+0x30`) зберігається покажчик на виділений менеджер (68 байтів).
   - Конструктор менеджера (`803E32E8`) записує:
     - `manager + 0`: сигнатуру-магічне слово **`434F5250` ('PROC')**;
     - `manager + 56`: зворотний покажчик на `factory`;
     - `manager + 60`: індекс процесора `0`.

2. **Менеджер → Плата (`board`)**:
   - Функція setup менеджера (`803E3348`) для процесора 0 виділяє 336 байтів під об'єкт `board`.
   - Конструктор `board` (`803EFFCC`) ініціалізує плату.
   - До повернутого покажчика додається 8 (`common board = board + 8`).
   - Покажчик `board + 8` зберігається у `manager + 44` (`+0x2C`).
   - Відповідно, базова адреса плати: `board = *(TUint32*)(manager + 44) - 8`.

3. **Плата → Контекст → Читач → Вікно DSP**:
   - `board + 236`: байт підтвердження обміну (`swap_byte`, ініціалізується як 1).
   - `board + 264`: покажчик на виділений контекст повідомлень (364 байти).
   - `context + 48`: перевірка узгодженості — має дорівнювати `board + 8`.
   - `context + 24`: покажчик на читача = `board + 172`.
   - `reader + 0`: базова адреса спільного вікна ARM для DSP.
   - `reader + 64`: байт підтвердження (має дорівнювати значенню за `board + 236`).
   - `context + 224`: заголовок черги `fromDSP`.
   - `context + 240`: масив записів `records = fromDSP + 8`.
   - `context + 16`: джерело черги; `context + 40`: активне очікування прийому.

## Проєкт безпечного bounded read-only snapshot

Для зчитування живого стану без модифікації пам'яті розроблено протокол покрокової валідації:

1. **Вхідний контроль**:
   - Перевірка MachineUid (`0x20002496` для E90).
   - Читання кореня контейнерів `0xC80019D4`.

2. **Валідація PDD-контейнера**:
   - Прочитати покажчик PDD контейнера зі слота `0xC80019FC`.
   - Перевірити діапазон адреси в межах ядра (`0xC8000000`–`0xC8100000`).
   - Зчитати заголовок контейнера (24 байти): лічильник `count` має бути `1 <= count <= 32`.
   - Перевірити адресу масиву покажчиків `iObjects`.

3. **Пошук фабрики за vtable**:
   - Прочитати покажчики об'єктів. Для кожного прочитати перше слово (vtable).
   - Знайти об'єкт із `vtable == 0x803F8380`.
   - Якщо об'єкт не знайдено — негайний вихід без аварії.

4. **Валідація менеджера**:
   - Зчитати покажчик за `factory + 48`.
   - Перевірити слово за `manager + 0` на рівність `0x434F5250` ('PROC').
   - Перевірити `manager + 56 == factory` та `manager + 60 == 0`.

5. **Обчислення адреси плати та контексту**:
   - Прочитати `common_board = manager + 44`.
   - `board = common_board - 8`.
   - Перевірити `board + 264` (контекст). Зчитати `context + 48` та звірити з `common_board`.
   - Зчитати `context + 24` (читач) та перевірити рівність `board + 172`.
   - Зчитати `reader + 0` (ARM базова адреса спільного вікна).
   - Зчитати `reader + 64` та `board + 236`.

6. **Зчитування черги повідомлень**:
   - Перевірити, що `context + 224` (заголовок `fromDSP`) лежить у межах спільного вікна.
   - Зчитати заголовок, зміщення та поточні значення черги без відкриття процесора DSP.

Всі операції читання виконуються виключно у власний буфер процесу в пам'яті користувача (user RAM).
Жодних записів у пам'ять ядра, системні регістри чи PRCM не відбувається.
