# Бенчмарк TMS320C55x проти ARM1136 на Nokia N95 8GB — звіт

Мета: виконати власний код на **TMS320C55x** усередині **OMAP2420** під
Symbian і виміряти його швидкодію проти **ARM1136**.

Це звіт про стан на 2026-08-10. Факти — у `findings.md` (кожен із джерелом:
підтверджений на апараті, виведений з коду ROM, або позначений як гіпотеза).

---

## 0. РЕЗУЛЬТАТ

Q15 dot-product, `n = 1024`, той самий вихідний код на обох боках, заміри в
одному завантаженні апарата:

| | MMAC/s | MAC/такт |
|---|---|---|
| **ARM1136** @324 МГц (виміряно) | 32.3 | 0.099 |
| **TMS320C55x** @220 МГц (номінал) | 55.6 – 88.1 | 0.253 – 0.400 |

> **C55x швидший приблизно в 1.7–2.7 раза за абсолютною продуктивністю
> і в 2.6–4.0 раза на такт.**

Діапазон, а не одне число, — навмисно: оцінки монотонно спадають зі
зростанням обсягу роботи (88 → 68 → 56 MMAC/s), бо що довше рахує DSP, то
більше його витісняє аудіо-стек, який ним володіє. Деталі й застереження —
`findings.md` §20.

## 1. Підсумок одним абзацом

ARM-бік бенчмарку готовий і виміряний на апараті. C55x-вузол збирається з
власного коду у завантажуваний DOFF і структурно не відрізняється від
виробничих вузлів Nokia. Міст до DSP розібрано повністю — від 39 C++-ординалів
до чотирьох родин команд ядра — і на живому апараті **зареєстровано наш
власний вузол та створено для нього задачу на C55x**. Не закрито останню
ланку: запуск вузла й обмін повідомленнями. Через це фінального числа
«DSP проти ARM» ще нема.

## 2. Що працює на апараті

```
ord32 Open(proc=0 DSP, flag=0, NULL) -> 0     хендл каналу 0x00030002
ord9  bind(A, C)                     -> 0
ord26 Load(Z:\resource\plugins\baseimage.dof) -> 0
ord6(A, UUID вузла з бази)           -> 0
ord4(A, &ref)                        -> 0     ref = 0x007003B0
DoControl(канал, fn=4, TBuf8<20>, &out) -> 0  taskHandle = 0x00008000
ord10/ord33 close                             апарат живий
```

Кожен крок був передбаченням з дизасемблера, яке справдилось. Зокрема
`ord4(A, NULL)` віддав рівно `-6 KErrArgument`, як і мало бути за кодом.

**ARM-базова лінія** (Q15, однакові дані з детермінованого LCG):

| ядро | час | MMAC/s | MAC/такт |
|---|---|---|---|
| DOT (8192×2000) | 508 мс | 32.2 | 0.098 |
| FIR (4096×32×200) | 990 мс | 26.5 | 0.080 |
| BLK (8192×2000) | 648 мс | 25.3 | 0.077 |

## 3. Головні технічні знахідки

**Увесь dspbridge живе в ядрі.** `bridgeapi.dll` — лише C++-фасад; DOFF-лоадер,
DSP MMU, RMS-протокол і mailbox — у `ehwaomap.pdd` (110 КБ) за LDD **`Hwa`**
(не `D32HWA` — це внутрішній рядок). Потрібна capability **MultimediaDD**.

**39 ординалів = три класи**, виведено зі структури aliased-пар `C1/C2`+`D1/D2`
і підтверджено двічі незалежно (з конструкторів і з розкладки `CBal`):
A (1–14, UUID/DCD, 8 Б), B (15–24, задача/вузол, 16 Б), C (25–39,
процесор/канал, 20 Б).

**Повна поверхня ядра:** `fn 0..10` (канал; `fn 4` = створення задачі),
24 команди пристрою `0x0400_00NN`, 18 живих команд задачі `0x0800_00NN`,
родина `0x0C00_00NN`.

**Формат DCD і DOFF розкодовано** з вузлів у ROM: 31 поле запису вузла,
дві секції реєстрації, заголовок DOFF із правилом контрольної суми
`checksum = ~(сума 8 попередніх слів)` — перевірено на чотирьох файлах.

## 4. Наш вузол на DSP

`ord26` (`PROC_Load`) кладе ядро на будь-якому невиконуваному DOFF — і на
нашому вузлі, і на штатному `pingdyn.dll55l`. Обійдено **прямим викликом
розбору** `0x80A5F0D4`: він наповнює user-side DCD, а смертельне завантаження
образу робиться окремо, далі в `ord26`.

Далі виявилось, що `ord6` не бачить **динамічного** вузла без записів
бібліотек фаз (типи DCD 3/4/5). У ROM їх ніхто не оголошує — там їх синтезує
сам `ord26`. Ми оголосили їх явно у власному `.dcd_register`, і вузол
знайшовся.

```
parse(loader, "E:/bench.dll55l") -> 0
ord7(A, наш UUID, args)           -> 0
ord4(A, &ref)                     -> 0
DoControl(fn=4, {0,0,ref,0,0})    -> 0   taskHandle 0x8000
```

Що це саме наш вузол — видно з структури за `ref`: там лежать
`BENCH_DSP_create/execute/delete`. Команди задачі віддають адреси в просторі
DSP (`0x300000xx`), тобто пам'ять під вузол виділено.

Пропущеною ланкою був окремий асинхронний крок `fn=5` (створення вузла) — я
його викликав раніше, бачив `0`, але не чекав на статус, тому вважав марним.
З правильним очікуванням:

```
DoControl(5) node-create -> 0, status 0   *** NODE CREATED ON THE C55x ***
node fn 7 -> 0, status 0                  (до створення: -18)
node fn 8 -> 0, status 0                  (до створення: -2)
```

Тобто ядро завантажило наш `bench.dll55l` на DSP, динамічний лоадер зарезолвив
зовнішні символи проти базового образу, і RMS викликав нашу фазу
**`BENCH_DSP_create()` на C55x**.

**Чотири незалежні докази, що це саме наш вузол:** успішний `node-create`;
імена `BENCH_DSP_create/execute/delete` у структурі вузла; виділені під нього
адреси у просторі DSP (`0x300000xx`); і те, що операції над вузлом змінили
результат з помилки на успіх рівно після його створення.

**Шлях даних.** Черга повідомлень виявилась глухим кутом: ординали 15–18
(`0x0C000001/2`) не використовує жоден модуль у ROM, і виклик кладе ядро.
Тому вимір побудовано інакше — **робота крутиться всередині фази `create`, а
час міряється на ARM**; фіксовані накладні скорочуються різницею двох прогонів
з різною кількістю повторів. Числа — у розділі 0.

## 5. Побічно виправлено

- **ARM-бік ніколи не збирався:** пробіл у шляху ламав `abld`→`makmake`
  (передається без лапок). Лікується junction'ом без пробілу, який тепер
  створюється поза деревом проєктів і знімається після збірки.
- **Бенчмарк був не матчений:** ARM рахував у 64 бітах проти 32 на DSP.
  Виправлено; еквівалентність доведено незмінними контрольними сумами.
- **`build.cmd` деплоїв несвіжий бінарник:** `ABLD.BAT` повертає 0 навіть коли
  `make` впав. Тепер ціль видаляється перед збіркою.
- **Два з трьох ARM-ядер міряють пам'ять, а не ядро** (DOT і BLK потоково
  читають по 16 КБ — більше за L1D). Тому ARM- і DSP-числа треба знімати в
  одному прогоні; між завантаженнями вони різняться в півтора раза при тій
  самій частоті ядра.

## 6. Методичні уроки (куплені помилками)

- **Одиниця спостереження — завантаження апарата цілком, не прогін.** Я тричі
  оголошував підозрюваного невинним за надто коротким вікном.
- **Не будувати причинність на таймінгу повідомлень людини.** Модель
  «відкладений ребут» була вигадана саме так і виявилась хибною.
- **Довжину функції не можна виводити з відстані до наступного ординала** —
  так `TLex` із сусідньої неекспортованої функції потрапив у опис `ord4`.
- **Контроль треба вибирати за доведеною властивістю.** Перший контроль на
  UUID вузла PING нічого не доводив: PING не був зареєстрований. Правильним
  виявився UUID, який реєструє сама база.
- **Ознака реального прогону** — рядки `OK <байти>` від PUT і свіжий `cmdline`
  у першому рядку логу. Без них падіння стосується стану апарата *до* команди.

## 7. Безпека

Нічого у флеш; усе рантаймове; ребут повертає апарат як був. Аудіо не
відбиралось — обрано Шлях A. Ребути траплялись лише на одному конкретному
виклику (`ord26` на вузлі), і для нього знайдено безпечний варіант: тримати
файл відкритим ексклюзивно, тоді замість падіння повертається `-14`.
