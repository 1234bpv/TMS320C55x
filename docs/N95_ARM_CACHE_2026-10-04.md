# N95: exact ARM cache path for the ring utility

In the saved N95 firmware, utility2 calls ordinal 378, then 376. The new
[machine audit](evidence/2026-10-04/n95-arm-cache-path-audit.json) traces both
entry points to the cache routines. It checks the identity of the kernel/utility
against the previous DMM audit: 46 concrete kernel sites and 10 branch targets;
it publishes 436 bytes / 109 instruction words of the selected ranges. The
phones and deployed binaries were not changed.

| Path | Address | CP15 operation | Completion of the selected routine |
|---|---|---|---|
| Ordinal378, clean MVA | 8006D66C | c7,c10,1 | DSB c7,c10,4 → return |
| Ordinal378, clean Set/Way | 8006D6A4 | c7,c10,2 | DSB c7,c10,4 → return |
| Ordinal376, invalidate MVA | 8006D638 | c7,c6,1 | return; the 52-byte routine has no explicit DSB |
| Ordinal376, clean-invalidate Set/Way | 8006D6F8 | c7,c14,2 | DSB c7,c10,4 → return |

The CP15 operation names are compared with the primary
[Arm ARM1136 TRM DDI0211I](https://documentation-service.arm.com/static/5e8e4306fd977155116aade2),
Table 3-77,3-99/3-100 and the CP15 c7 Flush operations, 3-105..3-107. This is a
reference for instruction semantics, not a check of the N95 kernel revision or of
the OMAP interconnect acknowledgement rules.

Both two-argument wrappers pass an internal mask 6: mask 0x2 selects data-cache
work, and mask 0x1 evaluates to zero and skips the instruction-cache work. The
concrete range/whole-cache branch is determined by the runtime cache
metadata/threshold; these were not read here. Both branches were checked,
including the loop backedges. The presence of DSB in clean is confirmed by the
exact instructions.

Clean is followed by invalidate or clean-invalidate. Therefore whole-cache
ownership matters: if the ARM creates a dirty line during DSP ownership, this
helper may write it over the DSP result. In the measured hosts, the ARM does not
access the ring before the notification completion and utility2. Short
invalidate has a different barrier tail; the full caller/context completion
contract is not proven by this narrow audit.

The DSB on the ARM completes the preceding operations of this kernel according to
its architectural contract. Its existence alone does not prove that the write of
another master, the DSP, completed in SDRAM before the mailbox notification.
Therefore the DSP endpoint publication gate remains open. The old reference
SPRU376A4.4.3.1 on pending/bypass was checked against the local primary text: it
concerns the CPU pipeline and does not establish an OMAP fence.

Reproduction: `tools/rev/audit_n95_arm_cache.py` reads the local saved ROM;
`tools/verify_n95_arm_cache.py` independently decodes 13 CP15 operations, checks
the range hashes, 10 branch destinations and 3 DSB tails from the published JSON.
When the ROM is available, it also checks all 109 words in the kernel itself. No
script has phone I/O.
