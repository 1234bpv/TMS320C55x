# DMM: таблиця сторінок і передавання власності

Початковий документ описував статичну підготовку D1. **Оновлення03.10:**
D0 завершено3/3 на обох; reserve/map і кільце перевірені на обох,
три повні серії є лише на N95. Поточний hardware статус, flags17,
CMM provenance та межі cache/lifetime — [DMM_RING](DMM_RING_2026-10-03.md).
Нижче збережено початкові статичні висновки, не поточний стан телефонів.

## Підтверджений firmware ABI

Однакові ділянки `bridgeapi` map wrapper і `ebridgeutil` dispatch на N95/E90
перевірено побайтово. Аудит також перевіряє 19 ARM інструкцій, 13 Thumb
halfwords, усі п'ять BL dispatch та actual kernel export targets.
E90 `ebridgeutil.ldd` отримано read-only GET із Z:\sys\bin (1260 Б).
Kernel/bridge — попередні збережені модулі конкретної прошивки.

```cpp
TInt Map(void* processor, TUint32 armAddress, TUint32 byteCount,
         TUint32 reservedDspAddress, TUint32* mappedDspAddressOut,
         TUint32 flags); // bridgeapi ordinal31
```

Wrapper рахує охоплені 4096-байтові сторінки з урахуванням початкового
зсуву адреси, виділяє `pageCount * 8` байтів і передає 24-байтовий payload
через control04000012. Параметри payload: ARM address, bytes, reserved DSP
address, flags, page-list pointer, page count. Таблиця тимчасова: після
DoControl wrapper звільняє її. Native PDD робить власну копію перед map.

**Один запис таблиці — два 32-бітні поля `{linearPage, physicalPage}`**,
а не один 64-бітний physical address. Fn1 вирівнює лінійну адресу вниз,
отримує physical через kernel ordinal245 `Epoc::LinearToPhysical`,
просувається по 4096 байтів та зберігає обидві адреси. Два інші fn1 BL —
ordinal719 `kumemget32`; виклику pin/unpin API тут немає. Це не виключає
окремого механізму незмінності native chunk і не доводить його.

## Кеш та власність

Контракт штатного utility:

```cpp
TUint32 address = /* valid live ARM virtual buffer */;
TUint32 bytes = /* owned range */;
util.DoControl(2, &address, &bytes); // pointers to values; not descriptors
```

Fn2 спершу викликає kernel ordinal378, потім376. Імена зіставлено з
[первинною таблицею експортів Symbian](https://raw.githubusercontent.com/SymbianSource/oss.FCL.sf.os.kernelhwsrv/master/kernel/eka/eabi/ekernu.def).
Перший — `SyncMemoryBeforeDmaWrite`, другий — `SyncMemoryBeforeDmaRead`.
Вони готують пам'ять відповідно до передавання memory→HW та HW→memory;
окремий after-read API документує усунення старих CPU cache даних.
[Офіційний контракт Cache](https://raw.githubusercontent.com/SymbianSource/oss.FCL.sf.os.kernelhwsrv/master/kernel/eka/include/kernel/cache.h).

Native N95 kernel range paths підтверджують clean і drain write buffer,
потім invalidate. На E90 перевірено actual kernel import ordinals;
внутрішні CP15 range routines E90 в цьому аудиті не аналізувалися.
[Точний N95 machine audit04.10](N95_ARM_CACHE_2026-10-04.md) додав
обидві threshold branches: clean MVA/SetWay закінчуються DSB;
invalidate MVA не має explicit DSB у своїй52-byte routine, whole-cache
clean-invalidate має DSB. ARM DSB не є DSP endpoint-publication proof.

**Висновок для D1:** цей helper завжди clean-ить перед invalidate.
Якщо CPU створив dirty cache line, поки DSP володіє її пам'яттю, clean
може затерти DSP result. Тому не можна ділити одну line між ARM-writable
та DSP-writable полями. Це висновок із порядку native викликів, а не
апаратний тест когерентності.

Для майбутнього probe:

1. Підтвердити allocation chunk attributes та lifetime сторінок до map.
   Власність буфера утримувати до успішних node stop/delete, unmap,
   unreserve. Translate адрес не замінює цього доказу.
2. Перед передаванням DSP очистити/підготувати всі передані lines;
   ARM більше їх не змінює до підтвердженого повернення власності.
3. Після DSP completion узгодити cache перед читанням. Відсутність
   ARM dirty data в цих lines має бути інваріантом, а не припущенням.
4. Публікувати notify лише після даних та перевіреного ordering.
   DSP cache/order і byte→word адресування підтвердити окремим probe.
5. Pending request чи failed teardown утримує mapping і буфер;
   вивантаження не є заміною drain/join.

## Запропонована область 16KiB TOTAL

### Окремі native physical pools

Додатковий аудит простежив два pool у PDD на обох прошивках: owner+244
утримує record; kernel ord242 виділяє фізичну RAM, ord60 створює
`DPlatChunkHw`, ord241 звільняє фізичні allocation. Record містить
physical/linear/bytes для обох pool та обидва chunk pointers.
Перевірено 23 інструкції, шість kernel import calls і raw attrs 0x1044.

Ці pool **ще не зв'язані з candidate ARM native buffer**. Тому їх
існування не є доказом pinning чи lifetime кільця. Runtime provenance
буфера має бути підтверджена окремо після D0; заборона base reload
також залишається потрібною для збереження shared processor state.

### Розкладка для подальшої реалізації

| Частина | Зсув, bytes | Bytes |
|---|---:|---:|
| Control/reserved; поля різних власників у різних cache lines | 0 | 1024 |
| 15 input slots по512 Б | 1024 | 7680 |
| 15 output slots по512 Б | 8704 | 7680 |
| Разом, чотири сторінки | — | **16384** |

Це розкладка для реалізації після D0, не перевірений ring.
Wire поля — явні16-bit sequence/slot/length/status, з незалежною
обробкою wrap індексу та generation. Cache line size/alignment слід
підтвердити; рознесення ARM/DSP control полів вибрати за цим результатом.
Кожен512-Б slot може зберігати32-Б header і480-Б payload, як protocol21.
Повна двобічна перевірка включає16/32-bit та4KiB межі й кілька обертів.

Після correctness: щонайменше три серії latency/bandwidth, пакетні
передавання кількох batch sizes, p50/p95/p99/max, submit CPU/wall,
байти за секунду та незмінні measured clocks. Старі stream timings
не є результатами DMM. D2 потребує цих вимірів, а не статичного audit.
