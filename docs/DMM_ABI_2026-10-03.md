# DMM: page table and transfer of ownership

The original document described the static preparation of D1. **Update
03.10:** D0 was completed 3/3 on both; reserve/map and the ring were checked
on both, and three full series exist only on the N95. The current hardware
status, flags 17, CMM provenance and the cache/lifetime limits are in
[DMM_RING](DMM_RING_2026-10-03.md). The initial static conclusions are kept
below, not the current state of the phones.

## Confirmed firmware ABI

The identical sections of the `bridgeapi` map wrapper and the `ebridgeutil`
dispatch on the N95/E90 were checked byte by byte. The audit also checks 19
ARM instructions, 13 Thumb halfwords, all five BL dispatches and the actual
kernel export targets. The E90 `ebridgeutil.ldd` was obtained by a read-only
GET from Z:\sys\bin (1260 B). The kernel/bridge are the earlier saved modules
of this specific firmware.

```cpp
TInt Map(void* processor, TUint32 armAddress, TUint32 byteCount,
         TUint32 reservedDspAddress, TUint32* mappedDspAddressOut,
         TUint32 flags); // bridgeapi ordinal31
```

The wrapper counts the 4096-byte pages covered, taking into account the
initial address offset, allocates `pageCount * 8` bytes, and passes a 24-byte
payload via control 04000012. The payload parameters: ARM address, bytes,
reserved DSP address, flags, page-list pointer, page count. The table is
temporary: after DoControl the wrapper frees it. The native PDD makes its own
copy before the map.

**One table entry is two 32-bit fields `{linearPage, physicalPage}`**, not one
64-bit physical address. Fn1 aligns the linear address down, obtains the
physical address through kernel ordinal 245 `Epoc::LinearToPhysical`, advances
in steps of 4096 bytes, and keeps both addresses. The other two fn1 BLs are
ordinal 719 `kumemget32`; there is no pin/unpin API call here. This does not
exclude a separate mechanism for keeping the native chunk unchanged, and it
does not prove one.

## Cache and ownership

The contract of the standard utility:

```cpp
TUint32 address = /* valid live ARM virtual buffer */;
TUint32 bytes = /* owned range */;
util.DoControl(2, &address, &bytes); // pointers to values; not descriptors
```

Fn2 first calls kernel ordinal 378, then 376. The names were matched against
the [primary Symbian export table](https://raw.githubusercontent.com/SymbianSource/oss.FCL.sf.os.kernelhwsrv/master/kernel/eka/eabi/ekernu.def).
The first is `SyncMemoryBeforeDmaWrite`, the second is `SyncMemoryBeforeDmaRead`.
They prepare the memory for the transfers memory→HW and HW→memory,
respectively; a separate after-read API documents the removal of old CPU
cache data.
[Official Cache contract](https://raw.githubusercontent.com/SymbianSource/oss.FCL.sf.os.kernelhwsrv/master/kernel/eka/include/kernel/cache.h).

The native N95 kernel range paths confirm clean and drain write buffer, then
invalidate. On the E90, the actual kernel import ordinals were checked; the
internal CP15 range routines of the E90 were not analyzed in this audit.
[The exact N95 machine audit 04.10](N95_ARM_CACHE_2026-10-04.md) added both
threshold branches: clean MVA/SetWay end with DSB; invalidate MVA has no
explicit DSB in its 52-byte routine, whole-cache clean-invalidate has DSB. An
ARM DSB is not a DSP endpoint-publication proof.

**Conclusion for D1:** this helper always cleans before invalidating. If the
CPU created a dirty cache line while the DSP owns its memory, the clean may
overwrite the DSP result. Therefore one line must not be shared between
ARM-writable and DSP-writable fields. This conclusion comes from the order of
the native calls, not from a hardware coherency test.

For the future probe:

1. Confirm the allocation chunk attributes and the lifetime of the pages
   before the map. Keep the ownership of the buffer until a successful node
   stop/delete, unmap, unreserve. Translating addresses does not replace this
   proof.
2. Before handing over to the DSP, clean/prepare all the transferred lines;
   the ARM no longer changes them until the return of ownership is confirmed.
3. After DSP completion, reconcile the cache before reading. The absence of
   ARM dirty data in these lines must be an invariant, not an assumption.
4. Publish notify only after the data and the verified ordering. The DSP
   cache/order and the byte→word addressing must be confirmed by a separate
   probe.
5. A pending request or a failed teardown keeps the mapping and the buffer;
   unloading is not a replacement for drain/join.

## Proposed 16 KiB TOTAL area

### Separate native physical pools

An additional audit traced two pools in the PDD on both firmwares: owner+244
holds the record; kernel ord 242 allocates the physical RAM, ord 60 creates
`DPlatChunkHw`, ord 241 frees the physical allocations. The record contains
physical/linear/bytes for both pools and both chunk pointers. 23
instructions, six kernel import calls and raw attrs 0x1044 were checked.

These pools are **not yet linked to the candidate ARM native buffer**.
Therefore their existence is not proof of the pinning or the lifetime of the
ring. The runtime provenance of the buffer must be confirmed separately after
D0; the prohibition of the base reload also remains necessary to preserve the
shared processor state.

### Layout for the further implementation

| Part | Offset, bytes | Bytes |
|---|---:|---:|
| Control/reserved; fields of different owners in different cache lines | 0 | 1024 |
| 15 input slots of 512 B each | 1024 | 7680 |
| 15 output slots of 512 B each | 8704 | 7680 |
| Total, four pages | — | **16384** |

This is a layout for implementation after D0, not a verified ring. The wire
fields are explicit 16-bit sequence/slot/length/status, with independent
handling of the index wrap and the generation. The cache line size/alignment
must be confirmed; the separation of the ARM/DSP control fields is to be
chosen according to this result. Each 512 B slot may hold a 32 B header and a
480 B payload, as in protocol 21. A full two-sided check includes the 16/32-bit
and 4 KiB boundaries and several wraparounds.

After correctness: at least three series of latency/bandwidth, packet
transfers of several batch sizes, p50/p95/p99/max, submit CPU/wall, bytes per
second, and unchanged measured clocks. The old stream timings are not DMM
results. D2 requires these measurements, not a static audit.
