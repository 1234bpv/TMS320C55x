# Початковий план досліджень: доступ до TMS320C55x на N95 8GB

Історичний план2026-08-09. Актуальне доручення/критерії — `work/PLAN.md`,
виконання — `work/FINAL_AUDIT.md`, поточні виміри — `docs/WSOLA.md`.
Номінальні частоти й початкові наміри нижче не замінюють нові hardware results.

Дата: 2026-08-09. Стан фактів — `findings.md`. Методологія і правила безпеки —
успадковані від `../SymbianOverclock/CLAUDE.md` (нічого у флеш, усе рантаймове,
не повторювати після двох невдач, міряти роботу а не напис).

## Мета

Дати виконання власного коду на TMS320C55x всередині OMAP2420 і **виміряти його
швидкодію проти ARM1136**, зробивши це багаторазово відтворюваним. Результат —
плацдарм для використання DSP в інших проєктах (кодеки, DSP-обчислення).

Успіх мінімальний (MVP): будь-яка **спостережувана** власна інструкція виконана
на DSP і результат повернуто на ARM. Успіх повний: матчений бенчмарк C55x vs
ARM11 з незалежно підтвердженими числами, апарат після тесту повністю робочий.

## Головна невизначеність, яка керує планом

DSP **вже зайнятий** прошивкою (аудіо-стек: `ebridge`/`mailboxipc`/`activeadsp`,
`findings.md` §3). Тому спершу розбираємо, як Symbian ним керує, і лише потім
обираємо між двома шляхами:

- **Шлях A — співіснування через міст Symbian.** Через `ebridge`/mailbox
  віддати DSP власний вузол/задачу (як Nokia DSP Gateway на Maemo). Найменший
  апаратний ризик; блокер — чи міст узагалі приймає довільний код.
- **Шлях B — керований відбір DSP.** Kernel-MMIO (через `memoryaccess.ldd` або
  примітив exec-коду ядра, §5 findings): загейтити DSP-домен у PRCM, зняти/
  повернути reset, налаштувати DSP MMU, залити C55x-образ у DSP-пам'ять
  (`dspmemmapper`), виставити boot-вектор, пустити, зібрати результат через
  mailbox/shared-mem, потім повернути DSP аудіо-стеку. Повний контроль, вищий
  ризик.

Вибір A vs B — **гейт після Фази 1**, не зараз.

## Фаза 0 — База знань і інструменти (паралельно, без апарата)

Мета: мати повну карту заліза і робочий toolchain для C55x.

0.1. **Дістати OMAP2420 Multimedia Processor TRM** (не C55x-мануали, а SoC).
     З нього — точні карти: PRCM (CM_FCLKEN/ICLKEN/CLKSEL для DSP-домену,
     RM_RSTCTRL/RSTST reset), CONTROL module (DSP/IVA boot config, `CONTROL_*`),
     **DSP MMU** (TLB/CAM/RAM регістри), **MAILBOX** (повна карта від бази
     `0x48094000`), карта пам'яті DSP у просторі L3 (DARAM/SARAM, куди мапиться).
0.2. **Витягти релевантні розділи локальних PDF** (SPRU312 + programming):
     boot-послідовність C55x, формат reset-вектора, IDLE-домени, EMIF/DARAM,
     набір команд для fixed-point ядер бенчмарка. (`pdftotext -layout` вже
     працює; чернетки в `out/`.)
0.3. **Toolchain для C55x.** Оцінити варіанти й обрати один:
     TI Code Composer Studio / `cl55` (asm+компілятор, генерує COFF),
     чи відкриті шляхи. Ціль: зібрати мінімальний `.obj`/сирий бінарник з
     відомим entry, вміти дістати raw code section (аналог зняття заголовка).
0.4. **Перевірити успадковану інфраструктуру на живому апараті:** deploy-демон
     піднімається, `deploy_net.ps1 put/run/get` працює, kernel read+exec
     примітиви SymbianOverclock відтворюються. Без цього Фази 3+ стоять.
0.5. **Скелет проєкту:** `src/` (ARM-проба-хост), `group/` (mmp/bld.inf як у
     сусідів), `tools/build.cmd` (клон з SymbianDeployDaemon), `out/` (не
     комітиться). Ціль-хост назвемо `dsptest.exe`.

Вихід Фази 0: `findings.md` доповнено картами регістрів; toolchain збирає
тестовий C55x-образ; апаратний канал підтверджено живим.

## Фаза 1 — Реверс DSP-стеку Symbian з ROM (без апарата)

Мета: зрозуміти, **як прошивка керує DSP**, і чи є легкий шлях.

1.1. Дизасемблювати (objdump, зняти `TRomImageHeader`; за потреби
     `syminflate.js`): `ebridgeutil.ldd`, `mailboxipc.dll`, `mrmailboxutils.dll`,
     `dspmemmapper.dll`, `activeadsp.dll`, `einfoadspplugin.dll`,
     `idspluginhandler.dll`. Артефакти в `out/asm/`.
1.2. **`ebridgeutil.ldd`:** зареєстроване ім'я драйвера, набір команд каналу
     (`DoControl`/`DoRequest`), чи експонує **завантаження коду / створення
     вузла** на DSP, чи лише керовані аудіо-операції. Резольв імпортів проти
     реального `ekern.exe` з дампа (метод SymbianOverclock §10).
1.3. **`mailboxipc.dll`:** формат повідомлень mailbox (протокол ARM↔DSP), які
     команди DSP-firmware розуміє. Дає модель для Шляху A і для інжекту.
1.4. **`dspmemmapper.dll`:** як DSP-пам'ять мапиться в ARM (фіз. адреси DARAM/
     SARAM, розміри, кеш-атрибути) — потрібно, щоб класти код/дані для DSP.
1.5. **`activeadsp.dll` (+ плагіни):** чи є user-side клієнтський API
     (`RActiveADSP`?), який відкриває канал; чи можна ним підсунути свій код.
1.6. **`memoryaccess.ldd`:** розібрати повністю. Чи дає user-side Read/Write за
     фіз. адресою і якої розрядності (§4 findings). Це може закоротити весь
     Шлях B до простого MMIO — і закрити відкрите питання сусіднього проєкту.
1.7. **Boot DSP:** знайти, який модуль і як вантажить DSP-firmware на буті (де
     лежить образ DSP у ROM, як знімається reset). Дає або механізм для
     повторення (Шлях B), або точку паузи (Шлях A).

Вихід Фази 1: у `findings.md` — модель керування DSP, рішення **A vs B** з
доказами, список конкретних команд/адрес для MVP.

## ГЕЙТ РІШЕННЯ — ПЕРЕГЛЯНУТО: Шлях A (див. `findings.md` §11–§12)

Крок 2 спершу схилив до Шляху B. Але скан Z: знайшов на апараті **повний набір
sample-вузлів TI dspbridge** (`ping/scale/dmmcopy/strmcopy` DOFF C55x) + Nokia
аудіо-**базу DSP/BIOS** (`baseimage.dof`) + **динамічний** PING (`pingdyn.dll55l`).
Це знімає головний сумнів Шляху A (DCD не закрита — динамічна реєстрація працює)
і дає готову мішень. **Обрано Шлях A** (вузол через `bridgeapi.dll`): менший ризик
(reset DSP не потрібен, аудіо ціле), санкціонований механізм, є шаблон вузла.

**Milestone 1 «Hello, DSP» — БЕЗ toolchain:** тригернути існуючий **PING-вузол**
(UUID `12A3C3C1-D015-11D4-9F69-00C04F3A59AE`) через `bridgeapi.dll` (attach →
node-allocate → create → run → ping-msg). cl55 НЕ потрібен → можна вести
автономно (реверс node-load API `bridgeapi.dll`).

**Milestone 2 «Бенчмарк»:** власний C55x-вузол з Q15-ядрами (шаблон — ping) —
тут потрібен **TI `cl55`** (C5500 CGT, безкоштовний, пропрієтарний; відкритого
C55x-асемблера нема) + node-опис/DCD. Встановлення cl55 — крок користувача.

> **Статус ARM-боку (2026-08-10, findings §16–§17):** реверс мосту зроблено.
> Увесь dspbridge — у ядрі за LDD `Hwa` (`ehwa.ldd` + `ehwaomap.pdd`), потрібна
> capability MultimediaDD. 39 ординалів `bridgeapi.dll` розкладено на три класи
> (A/B/C), усі 39 адрес звірено з живим апаратом. Знято повну поверхню ядра:
> 24 команди пристрою `0x0400_00NN`, 18 команд задачі `0x0800_00NN`, родина
> `0x0C00_00NN`. Знайдено еталонну послідовність у `CBal` (§17.5) — наш
> завантажувач її дзеркалить. Окремо полагоджено збірку ARM-боку, яка ніколи не
> працювала через пробіл у шляху.
>
> **Блокер:** апарат перезавантажується (§16.8, §17.6, §17.7). Одна причина
> ймовірно наша і вже усунена (`User::LoadLogicalDevice`), друга лежить поза
> нашим кодом (сусідній проєкт лишив у системі `dvfs_interface` і
> `RomPatcherPlus.Driver`; на 423 МГц апарат був у режимі з відомим
> авторебутом). Поки це не з'ясовано, прогони на апараті міряють шум.

> **Статус DSP-боку Milestone 2: закрито** (findings §13–§15). cl55 встановлено,
> ланцюг COFF→DOFF працює нативно на Windows, вузол має власний UUID і
> DCD-запис, форма DOFF збігається з виробничим вузлом Nokia. Обидва milestone
> тепер упираються в **одне й те саме**: ARM-завантажувач поверх `bridgeapi.dll`
> (реверс 39 ординалів під контракт §14.1) — і апарат для прогону.
> Побічно закрито Фазу 3.3: DSP-бічний прилад часу — `CLK_gethtime` /
> `CLK_countspms` з базового образу (§15.4).

Шлях B (керований відбір DSP, повна карта регістрів §8) лишаємо як запасний,
якщо DCD-реєстрація власного вузла на роздрібному апараті все ж виявиться
закритою.

## Фаза 2 — «Hello, DSP»: перша власна інструкція (на апараті)

Мета — make-or-break: **спостережувано** виконати власний код на DSP.

- **Шлях A:** через відкритий канал послати мінімальну власну операцію; довести,
  що виконався саме наш код (напр., DSP пише впізнаваний патерн у shared-mem,
  який ARM читає через `dspmemmapper`).
- **Шлях B:** мінімальний C55x-блоб «записати 0x5A5A у відому DARAM-комірку і
  зупинитись»; ARM гейтить домен, знімає reset, чекає, читає комірку, повертає
  DSP. (Дзеркало прийому SymbianOverclock, де блоб `mov r0,#0x5A; bx lr`
  довів виконуваність SRAM.)
- Обов'язково: таймаути на кожен крок (урок сусіда — зависання блокує весь
  канал доставки), відновлення стану DSP наприкінці, усе ризиковане — за явним
  аргументом проби.

Вихід: підтверджений факт «наш код на DSP виконується», задокументований.

## Фаза 3 — Бенчмарк C55x vs ARM11 (на апараті)

3.1. Обрати матчені ядра: (а) **DSP-профільне** — FIR / dot-product / блочний
     FFT у Q15 fixed-point (dual-MAC C55x проти ARM1136); (б) **нейтральне
     цілочислове** — щоб бачити межу поза сильним боком DSP. Плаваючу точку
     не використовувати (у C55x її апаратно нема).
3.2. ARM-бік: перевикористати вимірювальний каркас SymbianOverclock (лічильники,
     Mitr/s, витримка під навантаженням).
3.3. DSP-бік: інструментувати цикли (лічильник тактів DSP), однакове робоче
     навантаження, однакові дані, врахувати вартість передачі через mailbox/
     shared-mem окремо від чистого обчислення.
3.4. Нормувати на частоту (DSP ~220 МГц vs ARM 330 МГц) і дати і абсолютні, і
     per-clock числа.

## Фаза 4 — Заміри, перехресна перевірка, документація

- Кожне число — **двома незалежними приладами**, відтворено ≥2 рази (дисципліна
  доказів). Явно рознести «чисте обчислення DSP» і «обчислення + IPC».
- Записати у `findings.md`; короткий підсумок-звіт як у сусіда (`WRITEUP.md`).
- Переконатися: після тесту аудіо/DSP апарата працює (ребут як страховка, але
  ціль — коректне відновлення без ребута).

## Ризики й запобіжники

| Ризик | Запобіжник |
|---|---|
| Відбір DSP ламає звук до ребута | Спершу Шлях A; у Шляху B — зберегти/відновити стан DSP-домену; тест за явним аргументом |
| Зависання блокує канал доставки | Таймаути на кожен запит і на load/create драйвера; статичний `TRequestStatus`; канал не закривати після таймауту (урок SymbianOverclock §7) |
| Немає Kernel DevKit | Тільки чужі драйвери або exec-примітив ядра; свій LDD не збираємо |
| Стиснені DSP-модулі ROM | `syminflate.js` вже вирішує Symbian-deflate |
| Порядок байтів / розрядність MMIO | Регістри mailbox/PRCM — суворо 32-біт доступ (урок §10 сусіда) |
| Здогад видати за факт | Кожна адреса/поле звірені з кодом ROM або TRM; гіпотези позначені |

## Найближчі 3 кроки (щойно після цього плану)

1. Дістати OMAP2420 Multimedia Processor TRM і витягти карти PRCM/CONTROL/
   DSP-MMU/mailbox (Фаза 0.1).
2. Дизасемблювати `memoryaccess.ldd` і `ebridgeutil.ldd` — вони вирішують
   A/B-гейт (Фаза 1.2, 1.6).
3. Підняти скелет проєкту + перевірити deploy-канал на апараті (Фаза 0.4–0.5).
